# 5 人公平生图调度与容量保护

## Goal

在现有 4C8G、单 Next.js 进程、单一老张上游渠道（6 个逻辑配置入口、上游未设置并发限制）的条件下，增加全局公平调度、内存自适应降载、容量观测和排队反馈，使 5 人混合使用时稳定持续出图且避免 OOM。

## Requirements

* 所有实际生图调用进入同一个进程级调度器，默认全局并发 12。
* 每用户最多 3 个在途执行单元，按用户轮转，避免大任务独占。
* 6 个老张逻辑配置每个最多 2 个在途，但统一视为同一渠道做容量统计。
* RSS 按 2.2GB/2.8GB/3.2GB 水位将调度并发降为 12/8/4/0；系统可用内存低于 1.5GB 时进入保护模式。
* 队列最多 200 个等待单元；超过时创建任务返回 503 QUEUE_FULL。
* photo-fission 单任务默认并发 4，pose-fission 默认 2，但最终仍服从全局调度。
* 任务 API 增加可选队列/调度状态字段，保持现有调用兼容。
* 新增管理员容量接口，返回调度、内存和逻辑 Provider 状态，不泄露凭证与业务提示词。
* 取消任务能移除等待单元并中止在途调用。
* 本地增加公平性、并发上限、内存降载、取消和容量快照测试。
* 只修改本地仓库，不 SSH 写生产、不部署、不提交 Git。

## Acceptance Criteria

* [ ] 5 个模拟用户同时提交混合任务时全局在途从不超过动态上限。
* [ ] 每用户在途不超过 3，活跃用户不会被单个大任务饿死。
* [ ] 单个逻辑 Provider 在途不超过 2。
* [ ] 内存水位正确触发 12/8/4/0 四档并发。
* [ ] 队列满时 API 返回 503、错误码 QUEUE_FULL 和 Retry-After。
* [ ] 取消任务后等待单元不再执行，在途调用收到 abort。
* [ ] 前端能显示 queued/active/throttled/memory_guard 状态与队列位置。
* [ ] lint、typecheck、build 和调度器测试通过。

## Technical Approach

新增进程级 `image-work-scheduler`：提交执行单元时携带 userId、taskId、providerId、priority、resolution 和 AbortSignal。内部维护按用户分组的 FIFO 队列，使用 round-robin 选择下一用户，再检查全局/用户/provider/内存约束。现有 provider 调用入口统一包裹调度器，而不是让每个业务流水线各自放大并发。

## Decision

老张是单一上游渠道但未限制并发，因此不按 6 个独立渠道计算 IPM；6 个配置仅承担负载分散和故障切换。初始全局并发由本机容量限制为 12，每逻辑入口 2，并由运行时内存保护自动下降。

## Out of Scope

* 不引入 Redis/BullMQ、数据库迁移或多实例 PM2 cluster。
* 不修改生产 Nginx、sysctl、PM2 或环境变量。
* 本轮不保证进程重启后恢复函数闭包级等待单元；持久任务恢复留到后续数据库/队列阶段。
