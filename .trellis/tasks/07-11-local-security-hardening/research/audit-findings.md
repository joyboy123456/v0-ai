# 审计结论与修复边界

## 最高风险链路

1. `require-user.ts` 无条件信任客户端可控 `x-user-id`。
2. `proxy.ts` 未剥离该请求头，并把 `/api/cleanup` 列为公共路径。
3. cleanup 路由仅要求普通用户，底层清理遍历全局资产且不按 owner 过滤。
4. 前端允许在预览后修改日期，确认数量和实际删除条件可能不一致。

## 数据隔离

* 创建任务引用 inputAssetId 时未校验 owner。
* 收藏案例查询接收 userId 但未用于过滤。
* 全局案例删除路由缺少真实鉴权和管理员授权。

## 输入与资源安全

* 姿势 URL 可触发服务器任意 fetch。
* 远程图片校验未覆盖 DNS 解析、IPv6 和重定向。
* 本地上传与远程下载都没有硬字节上限，存在 OOM 风险。

## 稳定性

* OSS 探针失败时健康接口仍返回 200。
* OSS 重建脚本存在语法错误。
* saved pose / case store 仍使用非原子覆盖写。
* 前端任务轮询、收藏切换和案例请求存在响应乱序。
