## 1. 纵轴：七脉 = 七种资源预算 ★

| 脉 | 预算 | 失控时的典型表现 | 我们现状 | 我们目标 |
| --- | --- | --- | --- | --- |
| 感知 | 注意力 | 看到太多等于什么都没看见 | None | Heavy |
| 记忆 | 连续性 | 每次像第一次见用户，或被旧信息拖死 | Light | Medium |
| 推理 | 不确定性 | 所有问题都「深度思考」，或都不思考 | None | Medium |
| 行动 | 不可逆 | 外部世界状态失控，需要补偿甚至无法补偿 | None | Heavy |
| 反思 | 校正 | 输出永远是初稿 | None | Medium |
| 协作 | 分工 | 大家都知道一切，所以大家都被噪声淹没 | None | **None（刻意）** |
| 治理 | 信任 | 强能力没有边界就是强事故 | Heavy | Heavy |

三圈顺序：内圈（感/记/推/行）能用 → 中圈（反思）可靠 → 外圈（协作/治理）能上线。

> 「每个项目不需要在第一天就七脉全满，但架构师必须第一天就知道七脉在哪。你可以暂时不实现某一脉，但不能假装它不存在。」（`02`）

## 2. 横轴：六式 = 错误的传播路径 ★

| 式 | 动词 | 错误怎么跑 | 该防什么 | 我们用不用 |
| --- | --- | --- | --- | --- |
| Chain 链式 | 传 | 错误级联 | 缩短链、强化中间 schema | 用（护栏、提示链、进度账本） |
| Route 路由 | 选 | 错误分派 | 分类器可观测、可回退 | 用（分诊、工具调度、复杂度路由、审批门） |
| Parallel 并行 | 撒 | 错误聚合 | **关键在 merge，不在 fan-out** | 限用（仅文本层，图像层不并行） |
| Orchestrate 编排 | 协 | 错误分解 | 验证 plan | v2 用 |
| Loop 循环 | 转 | 错误复合 | 停止条件、评估信号、每轮改动幅度 | 用（但付费动作跳出循环） |
| Hierarchy 层级 | 分 | 错误放大或隔离 | 隔离、权限继承控制 | 不用（协作整行放弃） |

> 横轴不是流程图轴，是 **failure propagation axis**。选拓扑就是在选错误如何移动。（`02`）

### 感知（`06`～`10`）

| --- | --- | --- | --- | --- | --- |

### 反思（`26`～`30`）

| 模式 | 坐标 | 一句话 | 必记参数 | 适配 | 原文 |
| --- | --- | --- | --- | --- | --- |
| ★ 生成评审 | 反思×链 | Generator 出稿，Critic **只报问题无放行权**，确定性策略裁决 | issue 需 check+evidence 才 grounded；修订稿一律 UNREVIEWED；**事实独立 > 模型独立** | **高**（v2） | `27` |
| ○ 自愈循环 | 反思×循环 | 红灯→诊断→受限补丁→审查→独立重测，不行就回滚 | `max_rounds=3`；半径 ≤2x；相同 (signature,fingerprint) = 无进展；回滚后需恢复证明 | 低（仅运行故障） | `30` |
| ○ 技能包 | 反思×层级 | 可发现/按需加载/可执行/有边界/已验证的方法 | `TRIAL/VERIFIED/RETIRED`；只路由 VERIFIED；渐进披露；黄金题三道；复用率低于线自动降级 | 中（v3） | `28` |
| ○ 经验回放 | 反思（跨任务） | 召回→注入→采用→结果→信用分配→生命周期 | `effectiveness=0.7*old+0.3*signal`；初值 0.5；健康线 0.5；至少 5 次复用才判 | 低（v3） | `29` |

### 协作（`31`～`35`）—— 我们整行不做，但要知道为什么

| 模式 | 坐标 | 一句话 | 为什么我们不做 | 原文 |
| --- | --- | --- | --- | --- |
| 层级委派 | 协作×层级 | 主管保留父目标，拆成边界明确的子责任给隔离 Worker | 没有真实可拆责任面；删掉任何一个角色交付不少 | `32` |
| 扇出聚合 | 协作×并行 | 真实并行面扩出去，聚合器按覆盖/口径/冲突/来源收回 | 我们每路 20～60s + 真额度，扇出生图是成本爆炸 | `33` |
| 对抗评审 | 协作×— | 提案/举证/放行三权分离，异议进入状态转移 | **降级使用**：同进程单 Critic + 确定性 blocker 闸 | `34` |
| 交接链 | 协作×链 | 每次换手交结构化带版本交接包，验收通过才交控制权 | 单进程内无真正责任转移；其版本/digest/receipt 理念我们在 v2 借用 | `35` |

判定标准直接引原文思考题（`31`）：

> 「删除其中一个 Agent，最终交付会明确少掉什么？若不会，只是昂贵重复调用。」

### 治理（`36` 导论，无正文）

导论点名的四个关注维度：**准入**（能不能放行）、**追责**（谁做了什么、按哪版规则）、**爆炸半径**（最多影响多少）、**权限渐进与事故收回**。预告的模式：审批门（G1）、爆炸半径控制（G2）、渐进承诺（G3），可观测性改为横切（X1）。

导论给的三个可直接用的结构（我们 v1 就要）：

```text
ActionProposal    proposal_id, version, contract_digest, artifact_digest,
                  requested_by, action, resource_scope, idempotency_key,
                  risk, reversibility
PolicyRef         policy_id, version, content_digest
GovernanceReceipt receipt_id, control, proposal_digest, policy_digest,
                  decided_by, decision, issued_at
```

教训：故事里的旧实现 accepted 回执**不记规则版本**，形成「放过去规则消失」。另有**四眼原则**：改限额的人不能自己批。

## 5. 反模式清单 ★

### 最容易踩的七个

1. **把提示词当安全边界**。「请勿绕过」写在 system prompt 里不是控制，真边界在服务端代理、权限、凭证层。（`25`）
2. **只看最终任务状态**。任务最终 `success` 不代表供应商只收到一次提交，必须看**动作账**。（`21`/`22`）
3. **把供应商 timeout 当失败立即重试**。异常只说明没收到明确结果，不代表外部动作没发生。（`22`/`25`）
4. **用 `rollback_marked=True` 伪装已恢复**。`marked ≠ started ≠ succeeded ≠ external_confirmed`。（`25`）
5. **工具描述只写功能名，不写 `when_not_to_use`**。这是四个相似功能被模型混用的主因。（`22`）
6. **审批不绑版本**。用户确认了 A，系统执行的却是之后被改过的 B。（`23`/`34`）
7. **把图片里的文字自动当成指令**。不可信 source → 高风险 sink 的典型路径。（`24`）

### 感知

- 把分诊当删除（P3 是延迟加载，必须留可用 handle）
- P0/P1 没有硬保护，预算满了就把错误证据裁掉
- handle 不可操作（告诉模型有素材，却没给取数工具）= 伪检索
- 看到图就全保留为图；让视觉模型负责精确计算
- 每轮重复发送同一张图
- 没有业务 hint（同一张图是主体、细节还是背景，系统无法分发）

### 记忆

- 全量聊天历史进 prompt
- scratchpad 直通长期层（把猜测当事实）= 记忆投毒
- 只分存储不分读取（文件分层了，实际仍全量加载）
- 只做 todo list，没有目标契约/非目标/验收条件
- 让 LLM 在自然语言里传递 taskId / provider request ID
- 只在 session 结束时写盘
- 把失败原因压成「生成失败」（下一轮继续用同一参数）

### 推理

- 把「请逐步思考」当生产级 CoT
- 一个步骤塞多个判断（验证器、依赖、失效传播全废）
- 让模型自评替代验证器；把供应侧 thinking 当业务审计记录
- 只按字数 / 工具调用次数路由
- 把 lane 和 reasoning_mode 焊成一个枚举
- 同一 prompt 多采样几次就叫多视角
- 聚合器必须选出赢家（不允许 `verdict=None`）
- 没有新假设却重复执行（把推理问题变成额度浪费）

### 行动

- 把所有工具暴露给模型，再靠 Prompt 约束
- 会话配额当业务幂等（挡不住并发/重启）
- 用时间戳代替对象版本（TOCTOU）
- 业务代码能直接 import 真实 Handler（旁路）
- 把拒绝计入成功配额（恶意提案能耗尽合法额度）
- 允许 `restart_all`；让 LLM 直接改写 DONE 步骤
- 计划里复制所有实时参数（执行时用过期资产版本/额度）
- 把非空检查当事实校验；允许工件自证
- PRE 钩子字段缺失时默认放行（所以 schema 检查必须在最前）
- 只保护主路径（子 Agent / 内置工具 / 业务代码旁路同一套护栏）
- 忽略**组合绕行**：逐个动作合法，source-to-sink 整体越权

### 反思

- 自我评审谄媚（模型偏爱自己生成的内容）
- 只换模型不接外部事实（**事实独立比模型独立重要**）
- 只看总分不看风险证据覆盖率
- 新稿继承旧审批徒章；无限改稿
- 候选技能跳过 TRIAL 直接当 VERIFIED；把一次成功当资格
- 相关性幻觉（「导出了两遍所以成功」）；多条经验同得一份信用
- 改测试/放宽标准换假绿；回滚命令执行了但现场没恢复
- 把质量主观判定交给自愈循环

### 协作

- 三个人不等于三份责任（模糊委派 → 全做同一题）
- 只看单体 SUCCEEDED，不看组合覆盖/重复
- 把「你是高级研究员」当交付契约
- 上下文全量复制给子 Agent；会话隔离了却仍继承生产凭证
- 缺席被成功数掩盖；同源重复被当独立证据
- 评论写在墙上但不进入状态转移（“有评审” ≠ “评审生效”）
- 交接时转发整段聊天，或只传 `source_checked=true` 这种布尔

## 6. 三个可直接复用的工程工具 ★

### 6.1 模式选型卡：ASSESS → ROUTE → SELECT（`03`）

```text
1) ASSESS：给七脉打分 None / Light / Heavy（先不讨论框架和工具）

2) ROUTE：定主拓扑
   低协作 + 短任务      -> Chain / Route
   中等复杂 + 多步骤    -> Orchestrate / Loop
   多专家 + 宽任务      -> Parallel / Hierarchy
   高风险动作          -> Governance Route / Chain / Hierarchy 优先

3) SELECT：每个 Heavy 至少选一个模式；**第一版总数控制在 3～7 个**
```

### 6.2 双轴评审五问（`03`）

1. 这个 Agent 的七脉状态是什么（None/Light/Heavy）？
2. 每个 Heavy 功能落在哪个拓扑？
3. 主要错误传播路径是什么？
4. 哪些格子刻意留空，理由是什么？
5. 从 v1 到 v2 的升级路径是什么？

> 评审要从「感觉这个 Agent 不够稳」变成「推理×循环没有停止条件，治理×路由没有审批门」。

### 6.3 Compound Error 四条路（`03`）

任何设计项必须命中至少一条，否则它只是装饰：

1. 减少步数
2. 提高单步质量
3. 增加中间校验
4. fail fast

## 7. 三平面与 Harness 四问

### 7.1 三平面（`extra-02`）★

| 平面 | 负责 | 特征 | 我们的对应物 |
| --- | --- | --- | --- |
| 叙事平面 | 发散、创意、可能性 | 自然语言，模型在这里 Loop 才有意义 | 提示词正文、镜头语言、方案说明 |
| 控制平面 | 收敛、机械真值 | 离散信号，错一个字都不行 | assetId / taskId / featureType / model / 张数 / 额度 / 幂等键 |
| 调度平面 | 顺序、进度 | Workspace / DAG / 节点状态 | 计划步骤、进度账本、恢复包 |

两句必记：

> 「参数的记录和传递不能完全交给模型。确定性的值必须由程序机械掌控，每一个参数都需要有可审计的来源（Provenance）。」
>
> 「计划活在代码里，创意活在上下文里。」

还有一条判定什么值得上重循环的标准：**执行型 × 长程组合**，两个轴都过了才值得。我们的生图是执行型（花真钱、不可撑销），但目前是单步；是否变成长程组合取决于 [agent-design.md §13 问题 1](./agent-design.md)。

怕循环自己给自己打分的哲学根据（GEB 怪圈）：

> 「不要在循环过程中自己给自己打分。对循环本身的验证，必须来自于循环的外部。」

→ 对我们就是：机械平面真值、用户真实反馈、或换一个模型交叉校验。

### 7.2 Harness 四问（`extra-03`）★

评价一套 Agent Harness 好不好，只问四个问题：

1. **可重建性**：模型所见能不能从事实（事件账本）重建？
2. **执行一致性**：工具是不是都走同一条受控路径？
3. **副作用消除**：插件卸载 / 升级失败能不能清理干净？
4. **治理完备性**：生产配置能不能证明权限、审计、停止条件已挂载？

DeepSeek Harness 的三层结构（值得借的形状）：

```text
组合层  Profile（完整运行方式）/ Bundle（插件组）/ Patch（环境差异） → dump-config 展开
执行层  Turn → 多个 Step，每 Step = 一次模型请求及其工具调用
记录层  Session Log → deriveMessages 派生模型上下文 / UI / 恢复 / Fork / 回放 / 遥测
```

工具公共流水线（安全、审批、超时、重试、结果检查全放在这里，工具本体保持简单）：

```text
pre-step → 模型请求 → request → 工具调用
  → tools/pre-execute → monotonic guards（不可被后续推翻）
  → tools/execute（超时/取消/重试/指标）
  → tools/post-execute（阱断/替换）→ finalizeContent → tools/result（审计/遥测/UI）
```

最硬的一条不变量：**Model-visible means logged**。真正发请求前从 Session Log 重建 messages 并与实际传入的做结构化比较，不一致就 fail（log-reconstruction desync）。

⚠️ dsh 仍是 developer preview，不要照搫成生产内核；只借「三层分工 + 公共工具流水线 + 可重建不变量」这三个理念。
